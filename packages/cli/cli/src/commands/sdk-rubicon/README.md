# `fern sdk rubicon`

`fern sdk rubicon` translates the `cli` target of an `sdk-config.yml` (SDK Config v1) into a `generators.yml` for
Fern's CLI generator, `fernapi/fern-cli-generator`. It then takes the `cli` target out of `sdk-config.yml`, so
`generators.yml` owns it. It is the reverse of `fern sdk migrate`, for the `cli` target only.

Rubicon is a stopgap until Postman's own CLI generator ships. Everything it needs is in this folder plus one
registration in `cli.ts`, so removing it is one change (see [Removal](#removal)).

## Usage

```
fern sdk rubicon [--api <name>] [--config <path>] [--output <folder>]
                 [--generator-version <version>] [--force] [--dry-run] [--strict]
```

| Option | Meaning |
|---|---|
| `--api` | The API to translate in a multi-API project (`fern/apis/<name>/`) |
| `--config` | The SDK Config file to read, instead of the one in the fern folder |
| `--output` | The folder to write `generators.yml` to; the default is the folder of the SDK Config file |
| `--generator-version` | The fern-cli-generator version when the SDK Config file pins none; the default is 0.49.0 |
| `--force` | Replace a `generators.yml` that rubicon did not write |
| `--dry-run` | Print the planned file changes without making them |
| `--strict` | Treat warnings as errors |

Then generate the CLI remotely:

```
fern generate --group cli                                           # Fern's Fiddle
FERN_USE_SDK_GEN_API=true fern generate --group cli --version 1.0.0 # Postman's sdk-gen-api
```

The sdk-gen-api route needs `--version` (the CLI's own version; `generators.yml` has no field for it) and a generator
version with a Fern pool, which today is 0.49.0 only.

## What it writes

All changes are planned first and applied in one transaction: if any write fails, every file is restored.

| File | When | What |
|---|---|---|
| `generators.yml` | Always | A header comment, `default-group: cli`, `auth-schemes`, `api` and one `cli` group |
| `.rubicon/overlay-<id>.yml` | A spec has several overlays | Their actions concatenated, in order (Fern takes one overlay file per spec) |
| `fern.config.json` | The project has none | `organization` and `version: "*"` |
| `sdk-config.yml` | Other targets remain | The `cli` target removed, with a commented rollback block at the end of the file |
| `sdk-config.rubicon.yml` | Always | The `cli` target alone. If `cli` was the only target, this is `sdk-config.yml` renamed |
| `generators.legacy.yml` | It exists and runs no group | Renamed to `generators.legacy.pre-rubicon.yml` |

Why each of these:

- **The `cli` target leaves `sdk-config.yml`.** A plain `fern generate` fails when `sdk-config.yml` and a
  `generators.yml` group both select `cli`.
- **`default-group: cli`.** A plain `fern generate` then runs the `cli` group together with the targets left in
  `sdk-config.yml`. Use `--group cli` or `--target <language>` to run one of them.
- **`generators.legacy.yml` is set aside.** The Fern CLI refuses a folder that holds both `generators.yml` and
  `generators.legacy.yml`, and `fern sdk migrate` leaves the latter behind. Rubicon renames it only when it runs no
  group. If it still runs groups, rubicon stops; migrate or remove those groups first.
- **An existing `generators.yml`.** Rubicon overwrites one it wrote before (it starts with
  `# Generated by fern sdk rubicon`), and refuses any other unless you pass `--force`.

## Running it again

Rubicon reads `sdk-config.yml` when it still has a `cli` target, and `sdk-config.rubicon.yml` otherwise. Edit the
`cli` target in `sdk-config.rubicon.yml`, then run `fern sdk rubicon` again; it rewrites `generators.yml` and changes
no SDK Config file.

## Settings SDK Config cannot hold

The generator uses its own defaults for these, and rubicon prints which ones applied:

| Setting | Default | Where to set it in `generators.yml` |
|---|---|---|
| `binaryName` | From the API display name. With several specs, every generated name changes, so rubicon warns | `groups.cli.generators[0].config.binaryName` |
| `customCommands` | On | `groups.cli.generators[0].config.customCommands` |
| `profiles` | Off | `groups.cli.generators[0].config.profiles` |
| `rootGroup` | None | `groups.cli.generators[0].config.rootGroup` |
| Browser-login `client-id` | Not set: `fern generate` refuses to run | `auth-schemes.<scheme>.client-id` |
| Browser-login redirect pages | The CLI's built-in pages | `auth-schemes.<scheme>.success-redirect-url`, `error-redirect-url` |
| An empty OAuth token prefix | Fern's default prefix | `auth-schemes.<scheme>.token-prefix: ""` |

When rubicon overwrites its own `generators.yml`, it keeps these keys from the old file and prints each one it
kept. Every other edit to `generators.yml` is lost on the next run. Other generator options, such as
`splitTypeCrates`, are not kept.

If `sdk-config.yml` came from `fern sdk migrate` and has no `api.auth`, migrate may have dropped the whole auth block
(it does so when any scheme cannot be mapped). Add `auth-schemes` and `api.auth` to `generators.yml` by hand.

## How fields are treated

Every field that differs from its default gets one treatment:

- **Map**: a rule writes it to `generators.yml`.
- **Warn**: it has no effect on the CLI; rubicon warns.
- **Reject**: it cannot be honored; rubicon stops.
- **Ignore**: it has no effect, and no warning is needed.

The table starts from the hosted bridge's table (`hostedFieldTreatments.ts`, copied from sdk-gen-api); rubicon's
differences are in `fieldTreatmentOverrides.ts`. A field the table does not know is an error, so a newer SDK Config
field cannot slip through unreviewed.

Specs are read with Fern's own loader, so overrides, overlays and references to other files apply exactly as in
`fern generate`. Rubicon uses them to skip headers the spec already declares, and to find OAuth token operations.

## When not to use it

Once the hosted bridge in sdk-gen-api is on for your organization, keep the `cli` target in `sdk-config.yml` and
generate it with `FERN_USE_SDK_GEN_API=true fern generate --target cli`. Rubicon cannot tell whether the bridge is
on.

## Rollback

Rubicon prints the exact steps after each run. In short:

1. Delete `generators.yml` (or its `cli` group).
2. Restore the `cli` target: rename `sdk-config.rubicon.yml` back to `sdk-config.yml`, or copy the target back from
   the commented block at the end of `sdk-config.yml` and delete `sdk-config.rubicon.yml`.
3. If rubicon renamed it, rename `generators.legacy.pre-rubicon.yml` back to `generators.legacy.yml`.

## Diagnostic codes

Diagnostics print as `[severity] [CODE] path: message; action`. Paths are SDK Config paths, such as
`api.auth.schemes[0].location`.

| Code | Severity | Meaning |
|---|---|---|
| `RUBICON_NO_CLI_TARGET` | error | The SDK Config file has no `cli` target |
| `RUBICON_SDK_CONFIG_INVALID` | error | The SDK Config file does not load or validate. Only the `cli` target's publish credentials are resolved |
| `RUBICON_SEVERAL_CLI_TARGETS` | error | It has more than one |
| `RUBICON_EXPANSION` | error | The `cli` target does not expand to a valid SDK Config IR |
| `RUBICON_UNKNOWN_FIELD` | error | A field the treatment table does not know |
| `RUBICON_UNSUPPORTED_FIELD` | error | A field the CLI generator cannot honor (Reject) |
| `RUBICON_IGNORED_FIELD` | warning | A field with no effect on the CLI (Warn) |
| `RUBICON_UNOWNED_FIELD` | error | A Map field no rule writes (a rubicon bug) |
| `RUBICON_URL_SOURCE` | error | A spec given by URL; download it and use `path` |
| `RUBICON_SPEC_TYPE` | error | An AsyncAPI or GraphQL spec; the generator needs OpenAPI |
| `RUBICON_SPEC_MISSING` | error | A spec, override or overlay file does not exist |
| `RUBICON_SPEC_PARSE` | error | A spec does not load |
| `RUBICON_EXTERNAL_REF` | error | A reference to another file survived loading |
| `RUBICON_API_KEY_LOCATION` | error | An API key outside a header |
| `RUBICON_BEARER_PREFIX` | error | A bearer prefix; Fern's bearer scheme has none |
| `RUBICON_BEARER_HEADER` | error | A custom bearer header; Fern's bearer scheme has none |
| `RUBICON_AUTH_ALL` | error | A requirement naming several schemes at once; Fern has no `all:` |
| `RUBICON_ENDPOINT_SECURITY` | warning | Per-endpoint security drops the CLI's auth registration |
| `RUBICON_TOKEN_ENDPOINT` | error | No spec POST operation matches the OAuth token URL |
| `RUBICON_TOKEN_RESPONSE` | error | The token operation returns no `access_token` |
| `RUBICON_INFERRED` | warning | `get-token` properties were inferred by RFC 6749 names |
| `RUBICON_REFRESH_ENDPOINT` | warning | No spec POST operation matches the refresh URL |
| `RUBICON_OAUTH_FLOW` | error | An implicit or password flow |
| `RUBICON_OAUTH_SECOND_FLOW` | error | A second flow on one OAuth scheme |
| `RUBICON_PUBLIC_CLIENT_ID` | warning | A browser-login flow; add `client-id` before generating |
| `RUBICON_HEADER_IS_SCHEME_KEY` | warning | A header named after an API-key scheme key (written by `fern sdk migrate`); skipped |
| `RUBICON_MULTI_URL_ENVIRONMENT` | error | An environment with several URLs |
| `RUBICON_LICENSE` | error | A custom license without a file path |
| `RUBICON_UNTESTED` | warning | Several overrides files, or GitHub output |
| `RUBICON_ZIP_AS_FILES` | warning | Zip delivery; rubicon writes files |
| `RUBICON_MULTI_SPEC_BINARY_NAME` | warning | Several specs and no `binaryName` |
| `RUBICON_ROOT_SETTING_CONFLICT` | warning | A spec's `pathParameterOrder` differs from root's; Fern reads it only at root |
| `RUBICON_GENERATOR_VERSION` | error | A generator version that is not an exact version, such as `latest` |
| `RUBICON_UNPOOLED_VERSION` | warning | A generator version with no Fern pool; the sdk-gen-api route fails |
| `RUBICON_GENERATORS_EXISTS` | error | A `generators.yml` rubicon did not write; pass `--force` to replace it |
| `RUBICON_GENERATORS_CONFLICT` | error | The folder holds both a generators file and `generators.legacy.yml` |
| `RUBICON_LEGACY_GROUPS_ACTIVE` | error | `generators.legacy.yml` still runs groups |
| `RUBICON_RENAME_CONFLICT` | error | A file rubicon needs to create already exists |

## Tests

```
pnpm --filter @fern-api/cli exec vitest --run src/commands/sdk-rubicon
```

The round trip over Fern's own `cli` fixtures has a fast variant in the normal run and a Docker variant behind
`RUBICON_ROUNDTRIP=1`; see `__test__/fixtures/roundtrip/README.md`. It is the gate for bumping the Fern CLI, the
generator version or `@postman/sdk-config`.

## Removal

When Postman's CLI generator ships:

1. Delete this folder and `addSdkRubiconCommand` in `cli.ts`.
2. Add a changelog entry under `packages/cli/cli/changes/unreleased/`.
